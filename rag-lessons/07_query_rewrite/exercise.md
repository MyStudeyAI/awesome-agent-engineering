## 练习 1：换一个"指代不明"的问题
把 `RAW_QUERY` 改成带指代词的问题：

```python
RAW_QUERY = "那个怎么弄？上次说的那个表。"
```

**观察**：直接检索几乎肯定召不准（"那个"指什么向量检索完全懵）。HyDE 和多查询展开能否改善？

**思考**：对于这种极端模糊的问题，query 改写能救到什么程度？什么情况下必须靠"多轮对话历史"？（提示：HyDE 和多查询能"猜测"，但如果完全没有上下文，它们也只能瞎猜——这引出了对话型 RAG 需要带历史消息的需求）
> 有限，而且不稳定。

Query 改写能救：
> 口语化但语义完整的 query。
> 有错别字但能猜出意图的 query。
> 省略了部分关键词但领域明显的 query

Query 改写救不了：
> 指代完全缺失，例如“那个”“它”“上次说的”
> 没有对话历史、没有用户上下文、没有实体记忆
> 多轮对话中才存在的省略和指代

## 练习 3：增加子问题数量
把多查询展开从 3 个子问题改成 **5 个**：

```python
multi_prompt = (
    f"请把下面问题拆解成 5 个更具体的子问题...\n\n用户问题：{RAW_QUERY}"
)
# 同时修改 [:3] 为 [:5]
sub_queries = [q.strip() for q in sub_queries_text.split("\n") if q.strip()][:5]
```

**观察**：子问题更多，召回覆盖率有没有提升？延迟和成本呢？

**思考**：多查询展开是"子问题越多越好"吗？权衡点在哪？（提示：覆盖 vs 成本/延迟/噪声）
> 不是。多查询展开的收益是**可能覆盖率提升**，代价是成本、延迟、噪声。
> 权衡点 -> 覆盖提升是否大于成本、延迟和噪声增加。

## ✅ 完成本课后，你应该能回答
1. 为什么不能直接拿用户原话去检索？举两个"烂 query"的例子。
2. HyDE 的核心思想是什么？为什么用"假设答案"检索反而更准？
3. 多查询展开解决什么问题？适合什么场景？
> 解决单 query 表达不全、歧义、多约束、多跳、召回不足。
> 适合：复杂问题、对比问题、多条件问题、专业检索。
> 不适合：简单 FAQ、延迟敏感、成本敏感场景。
> 通常 3～5 个，配合 RRF 和 Rerank。

4. 查询路由是什么概念？什么问题该路由到 BM25、什么该路由到向量？
> 走 BM25：关键词、专有名词、合同编号、错误码、SKU、API 名、人名、精确短语。
> 走向量：自然语言描述、同义改写、模糊语义、长问题、概念解释。
> 走混合：大多数生产 query。
> 走 SQL/API：结构化查询，如“上个月销售额”。
> 走图数据库：关系多跳，如“A 和 B 的共同联系人是谁”。

5. 检索质量的两个维度（文档侧/问题侧）分别用什么手段优化？
> 文档侧：切分策略、元数据、摘要、父子块、混合索引、Rerank、去重、时效、权限。
> 问题侧：查询改写、指代消解、HyDE、多查询展开、查询扩展、意图识别、查询路由、历史压缩。

一句话：
> 问题侧负责把 query 变清楚，文档侧负责把文档排正确，历史侧负责让指代有据可查。
